# MCP directory model view and bounded retrieval

## Problem and scope

An observed research run repeatedly paged the MCP directory and schemas through `agent.read_tool_result`. The signed discovery result remains the complete enabled directory; this change reduces the data shown to the model during tool selection. It does not change server discovery, schema binding, approval, dispatch, or model configuration.

## Behavior

`search_mcp_tools` still records one complete, immutable result. Its payload includes the original discovery `query`. The model projection shows grouped `server_id`, `server_name`, and `tool_name` values, plus `total_tools` and `matched_tools`; descriptions and schemas stay in the original event. The initial projection applies the search query to server identity/name, tool name, and the **complete** description. Whitespace-separated query terms match with OR semantics. A zero-match projection reports `matched_tools: 0` alongside the nonzero `total_tools`; the model can clear or change the query without repeating discovery. The model must not treat directory matches as literature results.

`agent.read_tool_result` accepts `mcp_selector` with `{view:"directory",query?,server_id?}` to browse or refine the frozen directory, or `{view:"tool",server_id,tool_name}` to retrieve one complete original tool entry and schema. The initial result uses `{view:"directory",query_from_search:true}` so an arbitrarily long original query is read from the verified event rather than duplicated in the reference and each page. An explicit `query` cannot be combined with `query_from_search`; omitting both clears the filter. Server selection combines with the query. The reader validates run, project, conversation, sequence, event hash, event integrity, successful discovery, selector shape, and UTF-8 page boundaries before returning data. Original unselected `field=data` pagination remains available for compatibility.

Once discovery is recorded, the execution system message supplies a fixed host-generated sequence/hash/data reference and retrieval instructions even if context compaction removes recent event text. Only an event matching the current run/project/conversation and passing `verify()` qualifies. Tool-supplied descriptions, schemas, model_content, and query text are never copied into that system instruction. The complete model request, including the new system text, goes through the existing provider request validation; the separate `context_max_bytes` limit retains its context-only meaning.

## Verification and limits

A synthetic 247-tool catalog with long descriptions, UTF-8 text, and schemas serialized to 291,056 bytes. On that same fixture, the previous compact directory with 96-byte description previews was 34,219 bytes across 7 pages; the current name-only directory is 6,346 bytes across 2 pages. Reading the full original result without a selector required 40 pages, and reading one exact schema required 1 page. The first current model projection was 5,399 bytes. These are deterministic fixture sizes and page counts, not measured wall-clock improvement or token billing. Tests cover query terms, server scoping, zero matches, exact schema equality, long initial queries, oversized explicit-query errors, UTF-8 pagination, identity/hash rejection, and the reference after compaction. Real model and SSH acceptance remains separate from these deterministic tests.
